### VPCとサブネットの関係を説明してください。WebサーバーとDBを配置するなら、パブリック／プライベートサブネットをどう使い分けますか？

以下を含めて説明してください。

- CIDR表記の意味（例: `10.0.1.0/24`）
- パブリック／プライベートサブネットを分ける理由
- インターネットへ出る経路と、外部から入る経路の違い
- サブネットだけでアクセス制御が完結するか

### 自分の回答
- わからない

### レビュー

- 評価: 🔴
- 不足: VPCとサブネットの範囲、CIDR、パブリック／プライベートの経路と配置、アクセス制御との違い
- Q1のIP・サブネット・ルーティングを学んだ後に復習する

### 学習する観点

#### 1. VPCとサブネットの関係

- VPCは、クラウド上に作る論理的に分離されたネットワーク全体
- サブネットは、VPCのIPアドレス範囲を用途や配置先ごとに分割した小さなネットワーク
- AWSではVPCはリージョンに作り、各サブネットは1つのアベイラビリティゾーンに属する

#### 2. CIDR表記

- `10.0.1.0/24`の`/24`は、IPv4アドレス32ビットのうち先頭24ビットがネットワーク部分であることを示す
- 残り8ビットがホスト部分なので、この範囲には理論上256個のIPアドレスがある
- CIDRは、同じサブネットとして扱うIPアドレスの範囲を表す

#### 3. パブリック／プライベートサブネット

- パブリックサブネットは、ルートテーブルにInternet Gatewayへの経路があるサブネット
- プライベートサブネットは、Internet Gatewayへの直接経路を持たず、インターネットから直接接続させないサブネット
- 外部公開の入口となるロードバランサーはパブリック、アプリケーションやDBはプライベートに置く構成が一般的
- 小規模構成でWebサーバーを直接公開するならパブリックに置く場合もあるが、DBは通常プライベートに置く

#### 4. インターネットへ出る経路と外部から入る経路

- パブリックサブネットのリソースが直接通信するには、Internet Gatewayへの経路とパブリックIPアドレスなどが必要
- プライベートサブネットのリソースが外部APIなどへ出る場合は、通常NAT Gatewayなどを経由する。詳細はQ3で学習する
- NAT Gatewayを使った外向き通信はできても、インターネット側からプライベートなリソースへ新しく接続を始めることはできない

#### 5. サブネットとアクセス制御の違い

- パブリック／プライベートの区別は主にルートテーブルの経路で決まる
- サブネットを分けるだけでは、許可する送信元やポートまで制御できない
- Security Group、Network ACL、ルートテーブルなどを組み合わせて通信を制御する

### 学習後に説明できるようにすること

1. VPCとサブネットはそれぞれ何を表すか
   1. VPCは自分専用の仮想ネットワーク
   2. サブネットはVPCのIPアドレス範囲をさらに小さなネットワークに分けたもの
2. `10.0.1.0/24`の`/24`は何を意味するか
   1. CIDR表記
   2. IPv4アドレス32ビットのうち先頭24ビットがネットワーク部分という意味
3. ロードバランサー、アプリ、DBをパブリック／プライベートのどちらへ置くか、その理由
   1. ロードバランサーは、外部ユーザーからHTTPリクエストを受け付ける窓口なのでパブリック
   2. アプリは、外部から直接アクセスさせる必要がないのでプライベート
   3. DBは、アプリからの必要な通信だけを許可すればよいのでプライベート
4. プライベートサブネットから外部へ出る通信と、外部から入る通信は何が違うか
   1. 外部へ出る通信はアプリから開始した通信
   2. インターネット側からアプリへ直接、新しい接続を開始することはできない構成にする
5. サブネットを分けるだけでアクセス制御が完結しない理由
   1. サブネットを分けるだけでは通信の許可・拒否を十分に制御できないため、ルートテーブルやSecurity Groupなどを組み合わせ、LBからアプリ、アプリからDBなど必要な通信だけを許可する

### 学習確認（2026-09-29）

- VPCとサブネットの包含関係、およびCIDRのネットワーク部分を説明できている
- ロードバランサー、アプリ、DBの配置を、外部公開の必要性と結び付けて判断できている
- 外向きに開始する通信と、インターネット側から直接開始する通信を区別できている
- サブネットだけでなく、ルートテーブルやSecurity Groupを組み合わせる必要性を説明できている
- 表現の補足: VPCは物理的な専有ネットワークではなく、クラウド上で論理的に分離された仮想ネットワーク
- 経路の補足: プライベートサブネットからインターネットへ出るには、通常はNAT Gatewayなどへのルートが必要。詳細はQ3で確認する

- NATで送信元アドレスを変換する目的
  - わからない

### レビュー

- 評価: 🔴
- 修正点: プライベートIPは「個人用」ではなく、組織やVPCなどの私的ネットワーク内で使うアドレス。パブリックIPはインターネット上でルーティング可能なアドレスであり、ドメインとの対応は必須ではない

### 学習する観点

#### 1. プライベートIPとパブリックIP

- プライベートIPは、VPCや社内ネットワークなどの私的ネットワーク内で使う。インターネットではそのまま宛先や送信元としてルーティングされない
- パブリックIPはインターネット上で一意に識別され、インターネット経由でルーティングできる
- プライベートIPは「個人用」、パブリックIPは「ドメイン用」という区別ではない

#### 2. NATの目的

- NATはIPアドレスを変換する仕組み
- プライベートサブネットのリソースが外部へ通信するとき、送信元のプライベートIPをNAT GatewayのパブリックIPへ変換する
- 外部のAPIからは、NAT GatewayのパブリックIPが通信元に見える
- 戻ってきたレスポンスは、NATが元の通信との対応を基に内部のリソースへ返す

#### 3. AWSでの代表的な通信経路

1. プライベートサブネットのアプリが外部APIへの通信を開始する
2. プライベートサブネットのルートテーブルが、外向き通信をNAT Gatewayへ送る
3. パブリックサブネットにあるNAT Gatewayが、送信元を自身のパブリックIPへ変換する
4. NAT GatewayからInternet Gatewayを経由してインターネットへ出る
5. レスポンスは逆の経路でアプリへ戻る

#### 4. NATと外部公開の違い

- NAT Gatewayは、内部から開始した外向き通信とその戻り通信のために使う
- インターネット側からプライベートサブネットのアプリへ、新しい接続を開始する入口にはならない
- Todo APIを外部公開する場合は、パブリックなロードバランサーなどで通信を受け、プライベートなアプリへ転送する

#### 5. 外部APIへ接続できない場合の確認順序

1. DNSで外部APIのIPアドレスを解決できるか
2. プライベートサブネットのルートテーブルがNAT Gatewayを向いているか
3. NAT Gatewayが利用可能な状態で、パブリックIPを持っているか
4. NAT GatewayのあるパブリックサブネットからInternet Gatewayへのルートがあるか
5. Security GroupやNetwork ACLが必要な送信・戻り通信を許可しているか
6. 接続先のIPアドレス・ポートが正しいか

### 学習後に説明できるようにすること

1. プライベートIPとパブリックIPは何が違うか
   - プライベートIPはVPCなどの内部ネットワークで使用されるIPアドレス
   - パブリックIPはインターネット上で使用されるIPアドレス
2. NAT Gatewayは送信元IPアドレスを何から何へ変換するか
   - プライベートIPからNAT GatewayのパブリックIPへ変換する
3. プライベートサブネットから外部APIまで、どの経路を通るか
   - アプリ → プライベートサブネットのルートテーブル → NAT Gateway → Internet Gateway → インターネット → 外部API
4. NAT GatewayだけでTodo APIを外部公開できないのはなぜか
   - NAT Gatewayは内部のリソースから開始する外向き通信を可能にするもので、インターネット側から新しい接続を開始する入口ではないため
   - Todo APIを外部公開する場合は、ロードバランサーなどの別の入口が必要
5. NAT経由で外部APIへ接続できない場合、何を順番に確認するか
   - DNS、プライベートサブネットのルートテーブル、NAT Gateway、NAT Gateway側のパブリックサブネットのルートテーブル、Internet Gateway、通信制御、外部API側を確認する

### 学習確認（2026-09-30）

#### 3. リバースプロキシとの関係

- `curl`が接続タイムアウトする場合は、DNSの次にあるIP経路やTCP接続を調べる

#### 2. 接続先と待ち受けの確認

- `curl -v`などで、実際に接続しようとしているIPアドレスとポートを確認する

- 送信元と接続先のルートテーブル、Internet Gateway、NAT Gatewayなど必要な経路を確認する
- Security Group、Network ACL、OSのFirewallで必要な通信が許可されているか確認する

- TCPのSYNを送っているか、SYN-ACKが戻っているかなどを確認し、送信できていないのか戻りがないのかを切り分ける
- `tcpdump`だけでは、別機器のルートテーブルやSecurity Groupの設定内容そのものまでは分からない
