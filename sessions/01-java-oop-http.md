## Q2（オブジェクト指向）

### カプセル化・継承・ポリモーフィズムをそれぞれ説明してください

できれば、実務ではどのような場面で使われているかまで話してください。

### 自己評価

🔴

### 自分の回答
- カプセル化
  - スコープを狭めることで意図しない変数の変更をなくすやりかた
- 継承
  - クラスの一部分だけ変更したい時などに継承することで柔軟な変更ができる
- ポリモーフィズム
  - わからない

### 改善版

- **カプセル化**: データとそのデータを操作する処理をクラスにまとめ、内部状態を外部から直接変更できないようにすることです。変更方法をメソッド経由に限定することで、不正な状態を防ぎます。
- **継承**: 既存クラスの性質や振る舞いを子クラスが引き継ぐ仕組みです。「子クラスは親クラスの一種である」という関係を表す場合に使います。単なるコード再利用が目的なら、親子間の結合を避けるため委譲も検討します。
- **ポリモーフィズム**: 共通のインターフェースや親クラスを通して、実装の異なるオブジェクトを同じ方法で扱える性質です。例えば、通知処理をインターフェースにしておけば、呼び出し側を変えずにメール送信やSlack送信へ実装を切り替えられます。

Springでは、Serviceがインターフェースに依存し、具体的な実装をDIで受け取る構造などに応用されています。

また、実務ではどのように使い分けるかも説明してください。

### 自分の回答

### 改善版

Listは要素を順序付きで保持し、重複を許可するコレクションです。インデックスを使って要素を取得できます。

Setは基本的に要素の重複を許可しないコレクションです。重複を排除したい場合や、ある要素が含まれているかを効率的に確認したい場合に使います。

実務では、Todoの一覧のように順序を持った複数件を扱う場合はListを使います。ユーザーの権限やTodoのタグなど、同じ値を重複させたくない場合はSetを使います。

`ArrayList`の要素検索は基本的にO(n)、`HashSet`は適切な`hashCode`実装があれば平均O(1)です。独自クラスを`HashSet`で正しく扱うには、`equals`と`hashCode`を整合するように実装します。

### 深掘り質問のレビュー

総合評価: 🟢（基礎レベル）

#### 1. 順序と重複

評価: 🟡

Listが順序を保持し、Setが重複を許さないことは説明できている。ただし、比較としては次の2軸を両方述べると明確になる。

評価: 🟢

評価: 🟢

> `equals()`で同じと判定されるオブジェクトは、同じ`hashCode()`を返す必要があります。

## Q4（HTTP）

### HTTPメソッド（GET・POST・PUT・PATCH・DELETE）の違いを説明してください

さらに、Todo APIではどこで使ったかまで説明してください。

### 自己評価
🟡

### 自分の回答
- GETは取得系のAPIで使われる
- POSTは登録系のAPIで使われる
  - bodyに必要な情報を与えることができる
- PUTは更新系のAPIで使われてる
- PATCHはわからない
- DELETEは削除系のAPIで使用される

### 改善版

GETはリソースの取得、POSTは新しいリソースの作成、PUTは指定したリソース全体の置換、PATCHはリソースの一部更新、DELETEはリソースの削除に使います。

Todo APIでは、一覧・詳細取得にGET、Todo作成にPOST、全体更新にPUT、一部項目だけの更新にPATCH、削除にDELETEを使います。

安全とはリソースの状態を変更しない性質、冪等とは同じ操作を複数回実行してもサーバー上の最終状態が同じになる性質です。GETは安全かつ冪等、PUTとDELETEは冪等、POSTは通常どちらでもありません。PATCHの冪等性は更新方法によります。

## Q5（HTTP）

### HTTPステータスコードで以下はどのような意味ですか？

- 200
- 201
- 400
- 401

- 404
- 500

そして、Todo APIではどの場面で返すべきかも答えてください。

### 自己評価

🟡

### 自分の回答
- 200は取得成功
  - 201は登録成功
- 400はエラー
  - 401は認証エラー
  - 403はわからない
  - 404は処理のエラー
- 500はサーバーエラー

### 改善版

| コード | 意味 | Todo APIで返す場面 |
|---|---|---|
| 200 OK | リクエスト成功 | Todo一覧・詳細の取得、更新成功 |
| 201 Created | リソース作成成功 | Todoの新規作成 |
| 400 Bad Request | リクエストが不正 | 必須項目不足、形式不正、バリデーションエラー |
| 401 Unauthorized | 認証が必要、または認証失敗 | トークンがない、トークンが無効 |
| 403 Forbidden | 認証済みだが権限がない | 他ユーザーのTodoを操作しようとした |
| 404 Not Found | リソースが存在しない | 指定IDのTodoが見つからない |
| 500 Internal Server Error | サーバー内部の想定外エラー | 未処理の例外が発生した |

Todoの削除に成功し、レスポンスボディを返さない場合は`204 No Content`を使えます。バリデーションエラーのレスポンスには、エラーコード、メッセージ、対象フィールドなどを含めます。予期しない例外の詳細は、内部情報の漏えいを防ぐためクライアントへそのまま返しません。
