- 注意点: ユーザー固有・認証済みレスポンスは共有キャッシュから他人へ返らないよう、`private`や`no-store`などを要件に応じて設定する

### 学習する観点

#### 1. HTTPキャッシュを使う目的

- 一度取得したレスポンスをブラウザなどに保存し、再利用する仕組み
- 同じデータを毎回サーバーから送り直さず、通信量・待ち時間・サーバー負荷を減らす
- ただし、更新されたデータではなく古いキャッシュを返す可能性があるため、鮮度の制御が必要

#### 2. `Cache-Control`で何を制御するか

- `max-age=60`: 取得後60秒間は新鮮なキャッシュとして再利用できる
- `no-cache`: 保存はできるが、使う前にサーバーへ変更の有無を確認する
- `no-store`: レスポンスを保存しない
- `private`: ブラウザなどの利用者専用キャッシュには保存できるが、CDNなどの共有キャッシュには保存させない
- 注意: `no-cache`は「保存しない」ではない。「保存しない」は`no-store`

#### 3. `ETag`による再検証

1. サーバーがレスポンスに、内容を識別する`ETag`を付ける
2. クライアントが次回、`If-None-Match`に以前の`ETag`を入れて送る
3. サーバーが現在の`ETag`と比較する
4. 変更がなければ`304 Not Modified`、変更があれば新しいレスポンスを返す

#### 4. `Last-Modified`による再検証

1. サーバーがレスポンスに最終更新日時を示す`Last-Modified`を付ける
2. クライアントが次回、`If-Modified-Since`にその日時を入れて送る
3. その日時以降に変更がなければ`304 Not Modified`、変更があれば新しいレスポンスを返す

#### 5. `ETag`と`Last-Modified`の使い分け

- `ETag`: 内容を表す識別子で比較するため、内容の変更をより正確に判定しやすい
- `Last-Modified`: 最終更新日時で比較するため分かりやすいが、短時間の複数更新などを正確に区別できない場合がある
- 両方が送られる場合もある。面接では、まず`ETag`を内容、`Last-Modified`を更新日時による再検証と説明できればよい

#### 6. `304 Not Modified`の意味

- リソースが変更されておらず、クライアントが保存しているキャッシュを再利用できるという意味
- 通常はレスポンス本文を送り直さないため、通信量を減らせる
- `304`自体がキャッシュのデータを返すのではなく、保存済みのデータを使ってよいと伝える

#### 7. 認証情報を含むAPIの注意点

- ユーザーごとに異なるTodo一覧などが共有キャッシュへ保存されると、別ユーザーへ返る危険がある
- 機密情報は要件に応じて`Cache-Control: no-store`を使う
- ユーザー専用のレスポンスを保存可能にする場合も、共有キャッシュを避けるため`private`を検討する
- 「高速化できるからキャッシュする」ではなく、データの機密性と古くなってよい時間を考えて決める

### 学習する観点

#### 1. フォワードプロキシ

- クライアント側の代理として外部サーバーへアクセスする
- 外部サーバーから見ると、実際のクライアントではなくフォワードプロキシがアクセス元に見える
- 組織内からのアクセス制御、通信記録、キャッシュなどに使われる

#### 2. リバースプロキシ

- サーバー側の代理としてクライアントからのリクエストを受け、内部のアプリケーションサーバーへ転送する
- クライアントは背後にあるアプリケーションサーバーの構成を意識しない
- TLS終端、負荷分散、キャッシュ、パスによる転送先の振り分け、内部サーバーの隠蔽などに使われる

#### 3. `curl`で確認すること

- APIへ接続できるか
- HTTPステータスコード、レスポンスヘッダー、レスポンス本文
- `curl -v`を使うと、接続先、TLS接続、送受信したHTTPヘッダーなどを詳しく確認できる
- 例: `curl -v https://example.com/api/todos`

#### 4. `dig`で確認すること

- ドメイン名が期待するIPアドレスへ名前解決されるか
- A・AAAA・CNAMEなどのDNSレコード、TTL、応答したDNSサーバー
- HTTPの状態は確認できない。`dig`はDNS、`curl`は接続・TLS・HTTPの確認に使う

#### 5. APIへ接続できない場合の切り分け順序

1. DNS: `dig`で期待するIPアドレスを返すか確認する
2. TCP接続: 対象ホストとポートへ接続できるか確認する
3. TLS: 証明書、有効期限、ホスト名、証明書チェーンを確認する
4. HTTP: `curl -v`でステータスコード、ヘッダー、本文を確認する
5. リバースプロキシ: 転送先やルーティング設定、プロキシのログを確認する
6. アプリケーション: アプリのログ、例外、DB接続などを確認する

### 学習後に説明できるようにすること

1. フォワードプロキシとリバースプロキシは、それぞれ誰の代理か
   1. フォワードプロキシはクライアントの変わりでサーバーからクライアントを隠し、リバースプロキシはサーバーの代わりでクライアンドからサーバーを隠している
2. リバースプロキシを置く目的を3つ挙げられるか
   1. 振り分け
   2. アプリケーションサーバーの前に共通の入り口を作ること
   3. キャッシュ
   4. ログ管理
3. `curl`と`dig`は何を確認するために使うか
   1. curlはHTTP/HTTPSにて通信してレスポンスを確認すること
   2. digはDNSを確認する
4. APIへ接続できない場合、DNSからアプリまでどの順番で調べるか
   1. まずはdigでDNSが正しいIPを返しているか確認をする
   2. 次にTCP接続できるか確認
   3. HTTPSであればTLSの証明書やハンドシェイクの確認
   4. その後curlなどでHTTPレスポンスの確認
   5. リバースプロキシを使用している場合はプロキシまで到達しているか、プロキシからアプリまで正常に転送できているかの確認
   6. 最後にアプリ内部のログやDBなども確認する

### 学習確認（2026-09-19）

- フォワードプロキシはクライアント側、リバースプロキシはサーバー側の代理であることを説明できている
- リバースプロキシの目的として、振り分け、共通の入口、キャッシュ、ログ管理を挙げられている
- `dig`はDNS、`curl`はHTTP/HTTPSの応答確認に使うと区別できている
- DNS → TCP → TLS → HTTP → リバースプロキシ → アプリの順で障害を切り分けられている
- 補足: プロキシは構成によりTLS終端やHTTP応答を担うため、HTTPの問題が見えたらプロキシのログ・転送先も確認する
